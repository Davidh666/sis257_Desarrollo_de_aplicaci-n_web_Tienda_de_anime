Akiba Store - Registro de cambios
================================

Objetivo
--------
Adaptar la interfaz y la API para los roles ADMINISTRADOR y VENDEDOR definidos
por la aplicación, manteniendo autenticación JWT y usando nombres camelCase en
los contratos TypeScript/Vue.

Autenticación y autorización
---------------------------
- El login devuelve id, usuario, nombreCompleto, rol, estado y accessToken.
  La contraseña nunca forma parte de esa respuesta.
- JwtAuthGuard y RolesGuard se aplican globalmente. Las rutas públicas se
  declaran expresamente con @Public().
- Se añadieron @Roles y RolesGuard, que responden con 403 cuando el usuario
  autenticado no tiene el rol requerido.
- Los tokens se validan contra usuarios activos y roles admitidos.
- JWT_TOKEN es obligatorio y debe tener al menos 32 caracteres.
  JWT_TOKEN_EXPIRATION es obligatorio y acepta duraciones positivas como
  60s, 15m, 1h o 7d. Se añadieron valores de ejemplo a
  backend_tienda_anime/.env.example; deben configurarse valores reales en el
  entorno local/de despliegue.
- Se mantiene clave con select:false, @Exclude() y hooks bcrypt
  @BeforeInsert/@BeforeUpdate. La consulta de autenticación selecciona clave
  únicamente para comparar el hash y devuelve un perfil sin ese campo.

Permisos implementados
----------------------
- ADMINISTRADOR: dashboard y operaciones administrativas; puede administrar
  productos, categorías, usuarios, clientes, ventas y detalles.
- VENDEDOR: consulta productos/categorías/clientes, registra clientes y crea
  ventas. Solo puede listar y consultar sus propias ventas. No puede modificar
  productos, categorías, clientes existentes, usuarios, ventas ni detalles.
- Las restricciones se hacen en el backend; los guards del router y menús
  condicionales del frontend son una segunda capa de navegación, no el control
  de seguridad principal.

Ventas e inventario
-------------------
- El vendedor asociado a una venta se obtiene del usuario validado por JWT;
  no se acepta usuarioId desde el cliente.
- POST /ventas recibe clienteId e items (productoId y cantidad). El servidor
  comprueba cliente/productos activos, bloquea y descuenta stock en una
  transacción, toma el precio desde la base de datos, calcula subtotales/total,
  genera el correlativo y crea los detalles de venta.
- Las lecturas de ventas de vendedor se filtran por usuarioId. Consultar una
  venta ajena devuelve 404. Actualización/anulación y eliminación quedan
  reservadas al administrador.
- Se añadieron las relaciones de detalle con producto para incluir datos de
  catálogo en las respuestas de ventas.
- Se alineó el nombre de la entidad Cliente con la tabla PostgreSQL `clientes`.

Frontend
--------
- Pinia valida y restaura la sesión, mantiene el rol tipado y limpia datos de
  sesión corruptos. El login consume accessToken en camelCase.
- El router incluye la ruta /forms, protege vistas privadas y redirige por rol.
- El Sidebar presenta navegación, nombreCompleto y acciones según el rol.
- AdminDashboardView muestra bienvenida y métricas consultadas al backend.
- ClientSalesView carga catálogo, clientes e historial, permite registrar un
  cliente, crear un carrito y emitir una venta; el backend recalcula precios
  y total.
- TablesView y FormsView implementan administración de productos y categorías,
  con edición y activación/desactivación en lugar de borrado físico.
- Los alias snake_case de transporte se retiraron de DTOs/serialización donde
  se exponían; se mantienen únicamente nombres de columnas DB en mapeos
  TypeORM, por ejemplo @Column({ name: 'nombre_completo' }).
- El interceptor Axios existente conserva Authorization: Bearer y limpia la
  sesión al recibir 401 (excepto errores de credenciales del endpoint login).

Archivos principales
--------------------
- backend_tienda_anime/src/auth/: guards JWT/RBAC, roles y configuración del
  token.
- backend_tienda_anime/src/ventas/: DTO, controller y servicio transaccional.
- backend_tienda_anime/src/{productos,categorias,clientes,usuarios,
  detalle_ventas}/: restricciones de rol y contratos/relaciones.
- frontend_tienda_anime/src/stores/auth.ts, router/index.ts y components/:
  sesión, navegación y datos del usuario.
- frontend_tienda_anime/src/views/: dashboard, punto de venta y CRUDs.

Actualización: configuración de entorno y registro público
=========================================================
- ConfigModule carga explícitamente el `.env` del directorio backend, tanto al
  iniciar desde la raíz del repositorio como desde `backend_tienda_anime`.
  TypeORM lee las variables DB_* mediante ConfigService y valida DB_PORT al
  iniciar; AuthModule/JwtStrategy consumen JWT_TOKEN y
  JWT_TOKEN_EXPIRATION desde la misma configuración. No se sobrescribió ni se
  documentó aquí el contenido privado de `backend_tienda_anime/.env`.
- `.env.example` quedó como plantilla con placeholders y los nombres exactos
  de variables requeridos. Copia la plantilla al `.env` del backend y configura
  credenciales locales propias; JWT_TOKEN debe tener al menos 32 caracteres y
  JWT_TOKEN_EXPIRATION acepta duraciones positivas como 60s, 15m, 1h o 7d.
- POST /usuarios es ahora público y crea siempre una cuenta activa con rol
  VENDEDOR, sin aceptar el rol desde el cliente. El nuevo DTO de registro solo
  expone usuario, nombreCompleto y clave; esta última se guarda con bcrypt y
  no se devuelve. La creación administrativa se mantiene protegida en
  POST /usuarios/administradores y fuerza rol ADMINISTRADOR.
- Swagger distingue el registro público de las operaciones protegidas:
  POST /usuarios no requiere Bearer; los endpoints administrativos conservan
  el esquema access-token y los guards globales JWT/RBAC.
- Se añadió /register al frontend con formulario, enlace desde Login y aviso
  de éxito. Las cuentas nuevas acceden al sistema como VENDEDOR; el router y
  los menús mantienen la separación de vistas por rol. La barra lateral solo
  se muestra en rutas protegidas.

Documentación interactiva Swagger
==================================
- @nestjs/swagger ya estaba declarado como dependencia del backend; se reutilizó
  sin cambiar package.json ni instalar una segunda versión.
- src/main.ts genera el documento OpenAPI y monta Swagger UI en la ruta exacta
  /api. Los endpoints de negocio conservan su prefijo/versionado /api/v1.
- El esquema Bearer usa el nombre access-token y el formato JWT. Los
  controladores protegidos declaran @ApiBearerAuth('access-token') y los
  controladores/DTOs principales documentan operaciones, respuestas, campos y
  ejemplos. El DTO de respuesta de login solo contiene el perfil y accessToken;
  no documenta ni devuelve clave.
- Para probar: abrir http://localhost:3000/api, ejecutar POST
  /api/v1/auth/login con usuario y clave, copiar accessToken de la respuesta,
  pulsar Authorize e introducir el token sin escribir el prefijo `Bearer`
  (Swagger lo agrega). Luego ejecutar una operación protegida. Los endpoints
  públicos de login y estado siguen sin exigir token.
- Swagger solo describe/ejecuta las rutas existentes: no sustituye ni desactiva
  JwtAuthGuard, RolesGuard, @Public(), los permisos por rol ni la protección
  bcrypt/select:false. No se leyó ni modificó backend_tienda_anime/.env.

Actualización: corrección de contraseñas y login
===============================================
- Usuario.clave conserva select:false y @Exclude(). Los hooks
  @BeforeInsert/@BeforeUpdate ahora hashean únicamente contraseñas en texto
  plano; reconocen hashes bcrypt existentes ($2a$, $2b$ y $2y$) para evitar
  que una actualización vuelva a hashear un valor ya protegido.
- El login consulta con QueryBuilder y `.addSelect('usuario.clave')`, necesario
  porque la columna se excluye por defecto. Las contraseñas bcrypt se comparan
  con `bcrypt.compare(claveIngresada, hash)` y la clave no aparece en el perfil
  que devuelve el servicio.
- Para compatibilidad con registros antiguos que guardaron texto plano, un
  acceso correcto se compara en tiempo constante y el hash se actualiza en la
  misma entidad. El hook de TypeORM convierte inmediatamente ese valor a
  bcrypt; los siguientes inicios usan `bcrypt.compare`. Las credenciales
  incorrectas siguen respondiendo 401.
- El registro público `POST /usuarios` continúa creando vendedores mediante
  `repository.save`, por lo que ejecuta los hooks y almacena la contraseña
  hasheada. No se añadió un seeder con contraseñas administrativas conocidas;
  cualquier administrador debe existir previamente o ser creado por la ruta
  administrativa protegida.
- Se añadieron pruebas para el hash idempotente, selección explícita de clave,
  login con bcrypt, migración de un registro plano heredado y rechazo de clave
  incorrecta.

Actualización: rol predeterminado de clientes
=============================================
- El registro público `POST /usuarios` y el default de creación ahora asignan
  `CLIENTE`. La propiedad rol del DTO valida `CLIENTE`, `VENDEDOR` o
  `ADMINISTRADOR` y usa CLIENTE cuando se omite; la columna TypeORM también
  declara `default: 'CLIENTE'`.
- El servicio fija CLIENTE para el registro público; la ruta administrativa
  conserva la asignación explícita de ADMINISTRADOR. La autenticación JWT y el
  DTO de login reconocen CLIENTE, sin concederle permisos de administrador o
  vendedor.
- Se adaptó el frontend para aceptar sesiones CLIENTE, dirigirlas a una vista
  de cuenta propia y bloquearles las rutas de ventas y administración. El
  formulario público ahora identifica claramente el registro como cuenta de
  cliente.

Actualización: ciclo de aprobación de pedidos
=============================================
- Las ventas de caja creadas por ADMINISTRADOR/VENDEDOR conservan el estado
  COMPLETADA. Los pedidos virtuales creados por CLIENTE se guardan como
  PENDIENTE y se vinculan directamente a `clienteUsuarioId`; no requieren que
  exista previamente un registro comercial en la tabla clientes.
- `POST /ventas/pedidos` valida productos y cantidades, calcula precios en el
  servidor y reserva stock dentro de una transacción. `PATCH /ventas/:id/estado`
  solo permite aprobar o rechazar pedidos pendientes y está restringido a
  ADMINISTRADOR/VENDEDOR. Al rechazar se libera el stock reservado; aprobar
  conserva la reserva. No se puede resolver dos veces un pedido.
- `GET /ventas` y `GET /ventas/:id` devuelven el historial de la cuenta CLIENTE
  autenticada filtrando por `clienteUsuarioId`; ADMINISTRADOR consulta todas
  las ventas y VENDEDOR solamente las propias. El alta/eliminación o el PATCH
  legado no pueden omitir la liberación de inventario de un pedido pendiente.
- Se añadió el panel administrativo `/admin-sales` para revisar y aprobar o
  rechazar pedidos, y `/purchases` para que CLIENTE haga pedidos y consulte el
  historial con badges: amarillo pendiente, verde aprobado y rojo rechazado.
  La consulta de productos es de solo lectura para CLIENTE.
- Se mantuvieron nullable los vínculos de vendedor y cliente comercial en
  ventas únicamente para pedidos de cuentas CLIENTE; las ventas de caja
  conservan sus asociaciones actuales. El esquema se actualiza mediante la
  sincronización TypeORM configurada en la aplicación.
- Validación de esta entrega: build y lint del backend, build del frontend y
  8 pruebas focalizadas del controller/servicio de ventas completados. La
  suite completa todavía reporta 8 suites fallidas (26 pruebas pasan) en tests
  heredados de módulos de categorías, clientes, productos y detalle de ventas
  que no configuran sus repositorios dependientes en TestingModule.

Actualización: unificación de clientes y usuarios
================================================
- Se eliminó la entidad `Cliente`, el módulo/controlador/servicio y sus DTOs y
  pruebas dedicadas. `AppModule` ya no registra `ClientesModule`; los perfiles
  de cliente se administran como filas de `usuarios` con rol `CLIENTE`.
- `Usuario` ahora conserva los datos opcionales nitCi, telefono y email. La
  columna clave sigue con `select: false`, bcrypt y @Exclude(), pero permite
  NULL para perfiles comerciales sin credenciales. Un perfil con clave nula no
  puede iniciar sesión; el login devuelve 401. El administrador puede asignar
  una nueva clave mediante la ruta protegida de actualización de usuarios, que
  pasa por los hooks bcrypt.
- Se añadió la migración PostgreSQL
  `src/migrations/1760000000000-ConsolidateClientesIntoUsuarios.ts`, habilitada
  en TypeORM al iniciar la aplicación. Migra cada fila de clientes a un usuario
  CLIENTE, conserva NIT/CI, nombre, teléfono, correo y estado, cambia las FKs
  de ventas a usuarios, consolida el vínculo anterior `cliente_usuario_id` y
  elimina la tabla clientes después de reescribir las referencias. No inventa
  contraseñas para los registros heredados.
- Para una venta de caja, ADMINISTRADOR/VENDEDOR consultan y crean perfiles en
  `GET/POST /usuarios/clientes`; el POST requiere Bearer y crea un perfil
  CLIENTE sin credenciales. El registro público `POST /usuarios` sigue
  solicitando contraseña, que se almacena con bcrypt, y acepta datos de
  contacto opcionales. Tanto ventas POS como pedidos online se vinculan por
  `ventas.cliente_id` a `usuarios.id`; `ventas.usuario_id` continúa guardando al
  vendedor cuando corresponde. El historial del cliente filtra por su mismo
  `cliente_id`.
- Dashboard y punto de venta consumen `/usuarios/clientes`; los listados no
  incluyen clave. Las vistas de ventas leen ahora el perfil mediante la
  relación `cliente` unificada.
- `database.sql` quedó alineado con PostgreSQL y ya no declara la tabla
  `clientes`; la FK de ventas referencia `usuarios`.
- La migración no es reversible automáticamente. Antes de desplegarla en una
  base con datos reales, realiza un respaldo y valida el resultado en un
  entorno de prueba. En una base nueva sin tablas, la migración no hace backfill
  y TypeORM crea el esquema consolidado.
- Validación: `npm run build` en backend y frontend, `npm run lint` en backend,
  y 21 pruebas focalizadas de migración, usuarios/controlador/ventas pasaron. El login
  selecciona solo los campos del perfil necesarios y no incluye contacto ni
  clave.

Actualización: duración de sesión JWT
=====================================
- Las sesiones JWT duran ocho horas (`JWT_TOKEN_EXPIRATION=8h`) y la
  configuración usa ese valor como respaldo cuando la variable no está
  definida.
- `JWT_SECRET` es el nombre principal para la clave de firma y validación. Se
  conserva `JWT_TOKEN` como respaldo compatible con configuraciones anteriores;
  la clave debe tener al menos 32 caracteres y no se incluye un secreto real
  en el código ni en `.env.example`.
- El frontend ya persiste el token en localStorage, lo envía como Bearer y
  limpia la sesión únicamente ante HTTP 401 de la API (exceptuando el login).

Actualización: acceso opcional para clientes del punto de venta
===============================================================
- El formulario de registro rápido en ClientSalesView permite ingresar
  usuario y clave opcionalmente. Si ambos quedan vacíos, se crea el perfil
  comercial sin acceso; al completar ambos, se envían junto con los datos del
  cliente. La interfaz rechaza credenciales incompletas y claves menores a
  seis caracteres.
- CreateClientePerfilDto acepta usuario y clave opcionales. El servicio
  genera un usuario único cuando el valor se omite o está vacío y rechaza
  nombres de usuario proporcionados que estén duplicados. Si no se proporciona
  clave, se guarda NULL; cuando existe, la entidad Usuario aplica bcrypt antes
  de guardar. La respuesta permite agregar y seleccionar el cliente creado.
